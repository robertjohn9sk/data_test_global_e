Implementation walkthrough

Data-processing process

This walkthrough records the processing logic and four SQL queries supplied by the candidate in this conversation. ChatGPT/Codex assisted with implementation, verification, documentation and the dashboard presentation.

  1. Read the unchanged source JSON from data/raw/orders_raw.json.
  2. Validate metadata record_count against the number of orders.
  3. Extract order ID, timestamp, status, channel, customer, sales representative, currency, shipping cost and payment method.
  4. Iterate through each nested line_items array.
  5. Assign a one-based line number within each order.
  6. Parse quantity, unit price and discount as Decimal for revenue calculations; quantity is stored as an integer.
  7. Calculate local revenue: quantity × unit_price × (1 − discount_pct / 100).
  8. Convert to USD using 1.00 for USD and 1.08 for EUR.
  9. Preserve the raw category and its standardized value.
  10. Load flattened orders and order_lines into DuckDB.
  11. Build dim_date, dim_customer and dim_product.
  12. Build fact_sales at line-item grain.
  13. Export all target tables to CSV.
  14. Execute the four reporting queries and export their results.
  15. Validate delivered revenue against 9,994.624060 USD, then refresh the public CSV copies.

Resulting warehouse model

orders

One row per order, including the customer snapshot and order-level shipping cost.

order_lines

One row per source item. Natural key: (order_id, line_number). Contains original currency, FX rate, raw and standardized categories, local revenue and USD revenue.

dim_customer

Historical customer segments using customer_key, effective_from, effective_to and is_current. Sarah Mitchell changes from Premium to VIP. Facts use the version effective on the order date; the first observed order date approximates the change date.

dim_product

One standardized record per product. Sports and Sports & Fitness map to Sports & Fitness; home appliances maps to Home Appliances.

dim_date

Date, year, month number and month name extracted from order timestamps in UTC. Contains observed order dates rather than a complete calendar.

fact_sales

One row per order line: order_id, line_number, date_key, customer_key, product_key, status, channel, currency, quantity, unit_price_usd, discount_pct and line_revenue_usd.

Revenue and data quality decisions

Only Delivered orders contribute to all four reports. Cancelled, Returned and Processing rows remain available for audit. Returned orders are excluded; no refund transactions are invented. Shipping is excluded from line revenue and remains at order grain to avoid double counting.

NULL or missing discounts default to zero. Monetary calculations use Decimal, with six decimal places stored for revenue and two displayed in reports. Category inconsistencies are normalized while preserving raw values. The €149.99 Yoga Mat price on ORD-2024-009 is flagged and retained because the source does not establish that it is incorrect.

SQL reports

Q1

-- Q1: Monthly delivered revenue trend
SELECT STRFTIME(date_key, '%Y-%m') AS month_label, ROUND(SUM(line_revenue_usd), 2) AS revenue_usd
FROM fact_sales WHERE status = 'Delivered' GROUP BY 1 ORDER BY 1;

Calculate delivered revenue by calendar month. GROUP BY 1 refers to the month_label expression.

Q2

-- Q2: Top products and share of delivered revenue
WITH product_revenue AS (
  SELECT p.product_name, SUM(f.line_revenue_usd) AS revenue_usd
  FROM fact_sales f JOIN dim_product p USING (product_key)
  WHERE f.status = 'Delivered' GROUP BY p.product_name
)
SELECT product_name, ROUND(revenue_usd, 2) AS revenue_usd,
       ROUND(100 * revenue_usd / SUM(revenue_usd) OVER (), 2) AS pct_total
FROM product_revenue ORDER BY revenue_usd DESC;

Aggregate product revenue first. SUM(revenue_usd) OVER () supplies the grand total so each product receives a percentage share.

Q3

-- Q3: Revenue by customer segment and channel
SELECT c.customer_segment, f.channel, ROUND(SUM(f.line_revenue_usd), 2) AS revenue_usd
FROM fact_sales f JOIN dim_customer c USING (customer_key)
WHERE f.status = 'Delivered'
GROUP BY 1, 2 ORDER BY 1, 2;

Join each fact to its historical customer version, then group revenue by segment and channel.

Q4

-- Q4: Customer order count, revenue, and revenue rank
SELECT c.customer_name, COUNT(DISTINCT f.order_id) AS total_orders,
       ROUND(SUM(f.line_revenue_usd), 2) AS revenue_usd,
       RANK() OVER (ORDER BY SUM(f.line_revenue_usd) DESC) AS revenue_rank
FROM fact_sales f JOIN dim_customer c USING (customer_key)
WHERE f.status = 'Delivered'
GROUP BY c.customer_name ORDER BY revenue_rank;

COUNT(DISTINCT order_id) prevents multi-line orders being counted repeatedly. RANK orders customers by unrounded revenue; ties share a rank and may leave gaps.

Scope and reproducibility

Run python src/pipeline.py to rebuild the warehouse and outputs. The supplied data produces 12 orders, 20 line items and 9 delivered orders. Delivered revenue is 9,994.624060 USD; the dashboard displays $9,994.62. The website reads exported CSV files; it does not execute SQL in a hosted database.

Customer history currently handles the observed segment change; repeated segment reversions and changes to other attributes need more general change detection. Q4 groups by customer name and includes delivered customers only; use customer_id as well when extending to duplicate names. Incremental loading is discussed in the README; this implementation rebuilds the small dataset.
